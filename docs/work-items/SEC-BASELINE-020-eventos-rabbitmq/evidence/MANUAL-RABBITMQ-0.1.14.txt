Security Baseline · Eventos RabbitMQ
1. Qué resuelve este flujo
Cuando se asigna o revoca un rol o perfil, el PDP genera un evento. RabbitMQ lo enruta solamente a la
cola de la aplicación afectada. Una aplicación X no consume mensajes de Y porque cada una usa una
cola distinta y un binding que coincide con su applicationId.
Regla principal
RabbitMQ decide el destino antes de que el consumidor vea el cuerpo. Para un cambio de Y, la
routing key es assignment.changed.<id-Y>; solo una cola enlazada con esa clave recibe el mensaje.

4. Crear la topología de una aplicación
Ejemplo real: la aplicación demo-integracion-v2 tiene applicationId 41ce1b83-a94e-49d7-a1fb-
ee6d1769ca0d. Reemplace ese UUID por el de otra aplicación si configura una nueva consumidora.
applicationId = 41ce1b83-a94e-49d7-a1fb-ee6d1769ca0d
Exchange: security.assignment.events
Queue: security.assignment.41ce1b83-a94e-49d7-a1fb-ee6d1769ca0d
Routing key: assignment.changed.41ce1b83-a94e-49d7-a1fb-ee6d1769ca0d
4.1. Crear el exchange
1. Abra http://localhost:25673 e inicie sesión con security-local.
2. Abra Exchanges y seleccione Add a new exchange.
3. Cree security.assignment.events con Type=direct, Durable=true y Auto delete=false.
4.2. Crear la cola
4. Abra Queues and Streams y seleccione Add a new queue.
5. Cree security.assignment.41ce1b83-a94e-49d7-a1fb-ee6d1769ca0d con Type=Classic y
Durable=true.
4.3. Crear el binding
6. Abra security.assignment.events y baje a Add binding from this exchange.
7. Seleccione To queue y escriba security.assignment.41ce1b83-a94e-49d7-a1fb-ee6d1769ca0d.
8. En Routing key escriba assignment.changed.41ce1b83-a94e-49d7-a1fb-ee6d1769ca0d. Arguments
queda vacío. Seleccione Bind.
Resultado esperado
La pantalla del exchange debe mostrar el binding hacia esa cola. Un evento publicado con otra
routing key, por ejemplo assignment.changed.<id-X>, no llega a esta cola.
5. Contrato que recibirá la consumidora
El cuerpo se publica como JSON con schemaVersion=1. La consumidora debe ignorar propiedades
adicionales compatibles, pero rechazar versiones no soportadas o applicationId ajeno.

6.3. Configuración de cola y binding
@Configuration
class AssignmentEventsRabbitConfiguration {
@Bean
Queue assignmentQueue(AssignmentEventsProperties p) {
return new Queue(p.queue(), true);
}
@Bean
Binding assignmentBinding(Queue assignmentQueue, DirectExchange exchange,
AssignmentEventsProperties p) {
return BindingBuilder.bind(assignmentQueue).to(exchange)
.with("assignment.changed." + p.applicationId());
}

6.4. Listener y caso de uso
@RabbitListener(queues = "${security.assignment-events.queue}", ackMode = "MANUAL")
void consume(Message message, Channel channel, @Header("amqp_deliveryTag") long tag)
throws IOException {
try {
AssignmentChangedEventV1 event = decode(message);
validateSchemaAndApplication(event);
applyAssignmentChangeUseCase.execute(mapper.toCommand(event));
channel.basicAck(tag, false);
} catch (PermanentContractException e) {
channel.basicReject(tag, false);
} catch (Exception e) {
channel.basicNack(tag, false, true);
}
}

Idempotencia de producción
No use un Set en memoria como solución final. Persistir eventId junto al efecto local o usar una
restricción única en la base de datos. Así reinicios y varias réplicas no duplican el efecto.

17. Cree la cola/binding de X con su propio UUID.
18. Publique assignment.changed.<id-Y>.
19. Solo la cola Y cambia; X conserva Ready=0 y no registra el evento.
8. Checklist de entrega
• ☐ RabbitMQ está healthy y se accede por http://localhost:25673.
• ☐ El exchange security.assignment.events es direct y durable.
• ☐ Cada aplicación usa applicationId, cola y binding propios.
• ☐ La consumidora valida schemaVersion y applicationId.
• ☐ La consumidora persiste eventId procesados y confirma después del efecto local.
• ☐ Se probaron mensaje válido, duplicado, contrato inválido y aislamiento X/Y.
• ☐ No hay credenciales Rabbit hardcodeadas en el repositorio de la consumidora.
